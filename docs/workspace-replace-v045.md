# Этап 13 — полная замена рабочего пространства

База PR: `fe1eb016be253a6446eec4da6aea65e5cb12526b` (main после PR #13).
Схема IndexedDB остаётся v3. Исторический HTML, PNG-эталоны и KF-001/KF-002 не изменяются.

## Процедура

В существующей проверке ZIP доступны «Добавить копии проектов» и «Заменить рабочее пространство». Второй режим разрешён только для `manifest.scope === 'workspace'`. Показаны количества проектов, документов, шрифтов и settings с обеих сторон, предупреждения о замене и ограничениях нескольких окон.

1. Закрыть все остальные окна приложения, включая старые версии и установленные PWA.
2. Открыть исходный ZIP и выбрать полную замену.
3. Создать страховочный ZIP. Текущее окно блокирует редактирование, получает исключительную Web Lock, завершает отложенный ввод и подтверждает сохранения активного и неактивных документов через существующие `zipSavedSnapshot`, `workspaceBarrier` и `readWorkspaceSnapshot`.
4. `createBackup` создаёт полный ZIP текущих четырёх stores и трёх разрешённых localStorage-настроек. Сам архив повторно читается через `readBackup`, вычисляется SHA-256 всего ZIP, затем файл передаётся браузеру для скачивания. Архив не записывается в IndexedDB как средство отката.
5. Пользователь сохраняет файл и повторно выбирает его с диска. Проверяются контейнер, JSON, связи, CRC и SHA-256 файлов через `readBackup`, затем SHA-256 всего ZIP сравнивается с только что созданной копией. Другой валидный ZIP, даже с теми же данными, не подходит. Галочка подтверждения не используется.
6. После успешной проверки ввести `ЗАМЕНИТЬ` и нажать кнопку замены. До этого она отключена. Повторный запуск блокируется состоянием диалога и сессии восстановления.

Любая ошибка подготовки/проверки отменяет сессию и требует заново открыть исходный ZIP и создать страховку. Отмена освобождает блокировку и возвращает редактирование. После страховочного снимка обычные записи текущего окна блокируются, включая `saveSoon`, `flushSave`, `saveDocumentSnapshot` и `dbOp`.

## Граница атомарности

`replaceWorkspace` повторно валидирует исходные ZIP-байты до открытия транзакции. Затем вызывает существующий `runStoreTransaction` ровно для `projects`, `docs`, `fonts`, `settings` в режиме `readwrite`.

В той же транзакции сначала читаются все четыре stores и сравниваются с исходным страховочным снимком. Если база изменилась, транзакция отменяется без очистки. Проверка и очистка находятся под одной блокировкой IndexedDB: между ними не может вклиниться другая транзакция записи. В обработчике последнего чтения синхронно ставятся все `clear` и `put`; `await` между запросами нет. Ошибка запроса вызывает штатный abort. Успех возвращается только после `transaction.oncomplete`. `deleteDatabase` и повышение версии схемы не используются.

Записываются исходные объекты ZIP без подготовки импорта копий: ID, даты, неизвестные поля, ресурсы, маски, шрифты и все записи settings сохраняются. Отсутствующие необязательные записи и пустые stores не заполняются до транзакции. После reload действуют существующие правила первого запуска (в частности, создание проекта и примера при пустой базе).

SHA-проверенный снимок описывает подтверждённые данные после обязательного завершения прежних сохранений. Обычное сохранение незавершённых правок до страховки является отдельным шагом; оно не входит в транзакцию замены.

Только IndexedDB заменяется атомарно. После commit применяются ровно:

- `kartochnaya-layer-width`;
- `kartochnaya-ink-v1`;
- `kartochnaya-shapes-v1`.

Отсутствующие в ZIP разрешённые ключи удаляются. Посторонние ключи, токены и пароли не переносятся и не изменяются. Отказ любого localStorage-действия собирается в явное сообщение о частичном восстановлении настроек. Уже завершённая транзакция IndexedDB не откатывается последующими записями. Информационные поля `manifest.globals` старого формата этапа 12 описывают режим копий; полная замена применяет globals согласно выбранному пользователем режиму.

После commit старый документ, вкладки и состояния сохранений очищаются, таймеры сохранения/жестов останавливаются, соединение базы закрывается. Блокировка старых записей остаётся включённой до уничтожения страницы. Выполняется `location.reload()`. Штатный запуск читает новую базу и выбирает запомненный проект только при наличии этого ID; иначе применяется обычный fallback. Метка результата в sessionStorage создаётся только после commit и потребляется при новом запуске. Ошибка навигации оставляет редактор остановленным с требованием перезагрузки вручную.

## Несколько окон и остаточные риски

Каждый экземпляр новой версии удерживает shared Web Lock `kartochnaya-workspace-v1` всю жизнь страницы. Для страховки и замены требуется exclusive lock с `ifAvailable`. Дополнительная exclusive lock начала операции (`-replace-intent`) берётся до освобождения своей shared lock: при одновременных попытках проигравшее окно сохраняет shared lock, поэтому победитель также отказывается от замены, пока это старое окно открыто. Если другое участвующее окно активно, операция отказывается начинаться. Новое окно, открытое во время страховки, ждёт освобождения lock до загрузки базы и запуска сохранений. При отсутствии Web Locks полная замена запрещена; обычное приложение и добавление копий продолжают работать.

Это ограниченный протокол, не общая синхронизация вкладок. **Старые версии приложения не удерживают эту блокировку и не могут быть надёжно обнаружены данным механизмом.** Они, сторонний код и инструменты разработчика могут писать непосредственно в базу. Проверка снимка ловит изменения до замены, но старое окно способно записать устаревшие данные после commit. Поэтому все остальные окна необходимо закрыть вручную; полная безопасность произвольных нескольких окон не заявляется. Другая origin/профиль браузера имеет отдельное хранилище и lock. Широкий рефакторинг всех путей сохранения и межверсионный протокол в PR не входят.

Браузер также не гарантирует сохранность скачанного файла в будущем. Повторный выбор доказывает наличие точных байтов на момент проверки; файл следует хранить вне данных браузера. Остаются прежние ограничения памяти ZIP этапа 12 (512 МиБ распакованных данных) и отсутствие общей транзакции с localStorage.

## Проверки

`tests/workspace-replace.test.mjs` проверяет функцию замены и сессию страховки через существующую тестовую IndexedDB. `tests/workspace-replace.spec.js` проверяет сгенерированное приложение в настоящем Chromium, читая фактические stores, а не только сообщения UI:

- два проекта с документами, исходные ID/даты/неизвестные поля, шрифты, каталог фигур и известные localStorage-ключи;
- отсутствие страховки, несовпадающий и повреждённый повторно выбранный файл, запрет selected-projects;
- abort после первого и третьего успешного `put`, настоящий ConstraintError после успешных записей, отказ открытия транзакции;
- изменение базы после страховки, отказ localStorage после commit;
- незавершённая настоящая транзакция сохранения, старые активные/неактивные вкладки, beforeunload, debounce и повторный запуск;
- другое активное окно, одновременные попытки в двух загруженных окнах с искусственно расширенным интервалом перехода блокировки, новое окно во время exclusive lock и отсутствие Web Locks.

Существующие ZIP-тесты этапа 12 также выполняются без изменения. Обратимый diff guard этапа 13 сохраняет прежние строгие проверки исторического исходника. GitHub Actions включает новые unit- и браузерные тесты.

## Откат

Для отката данных закрыть остальные окна, открыть скачанный страховочный ZIP и повторить полную замену. При этом приложение сначала потребует новую страховочную копию текущего состояния. Старый страховочный ZIP остаётся обычным полноценным архивом, пригодным для повторного восстановления; ошибка localStorage его не меняет. Если нужна только часть проектов, его можно открыть в режиме добавления копий с новыми ID.

Для отката кода после будущего merge — revert commit этого PR, пересобрать HTML/PWA и перезагрузить все окна. Revert кода сам по себе данные не возвращает. Схема v3 совместима с этапом 12; удалять базу браузера не требуется.
