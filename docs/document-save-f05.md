# F-05: подтверждённое сохранение и вкладки

База: `e2604260fbb255fef11dda2bdc71abe69e72ba4b`, актуальная `main` после merge PR #38.
Проверены GitHub PR, `git fetch origin main`, SHA и `AGENTS.md`.
Ветка: `fix/f05-document-save-lifecycle`. Merge и Production Deploy не выполняются.

## Воспроизведение до изменения реализации

Коммит `e46b318` содержит только тесты, подключение unit-suite и исходные измерения.
Реализация в нём совпадает с базой. [Машинный отчёт](document-save-f05-baseline.json)
содержит реальные ошибки, сериализованные документы до/после и наблюдения IndexedDB.

- Исходные unit: **5 passed / 5 failed / 0 skipped**.
- Исходные browser: **3 passed / 5 failed / 0 skipped**.
- Ещё четыре browser-сценария отдельно выполнены на неизменённой реализации
  в detached worktree `e46b318`: **0 passed / 4 failed**. Это завершение текста
  без правок, индикатор при вводе, отказ стартовой записи и переименование
  неактивной вкладки с ожидающими правками.
- Новые tests не используют `skip` или `test.fail`; существующие tests и fixtures
  не изменены. Проверки добавлены до исправления соответствующего поведения.

Подтверждённые причины:

1. **F-05A:** дедупликация только относительно `pending.key`; после завершения
   транзакции такой же снимок снова попадал в `readwrite`/`put`.
2. **F-05B:** `setDoc()` всегда планировал запись. Подготовка groups, slides,
   зеркала активного слайда и optional defaults превращалась в перезапись старой записи.
3. **F-05C:** последняя runtime-версия `changeSlide()` вызывала `saveSoon()` даже
   при повторном выборе активного холста. Реальная смена `activeSlideIndex`
   является сохраняемым изменением и продолжает сохраняться.
4. `saveSoon()` очищал ошибку до подтверждения новой попытки. Закрытие неизменённого
   текста безусловно меняло `updatedAt`; input менял модель при старом «Сохранено».
5. При отказе стартовой записи пример всё равно добавлялся в `app.docs`.
6. Переименование неактивной вкладки брало старую строку из `app.docs`, а не
   последнюю модель вкладки, и писало отдельно от snapshot-сохранений. В baseline
   после удержания записи X, двух изменений и переименования из главной страницы
   сохранённое содержимое X содержало **0 объектов вместо 2**.

Не объявляются новыми дефектами: Chromium уже упорядочивал реальные транзакции
одного store; сохранение изменённого документа во время предыдущей транзакции,
изоляция X/Y, завершение inline-текста при передаче контекста и отказ закрытия
неподтверждённой вкладки уже имели работающие контроли. Unit с обратным освобождением
задержек моделирует асинхронную подготовку **до создания** транзакции: он доказывает
порядок приложения, а не возможность переставить Chromium `oncomplete` у уже
созданных конфликтующих транзакций.

## Контроль подтверждений

Остаётся существующий `documentSaves`, без второго кэша. Один FIFO на документ:

| Поле | Значение |
| --- | --- |
| `saved` | Сериализуемое представление последней подтверждённой версии. Для прочитанной старой записи — её эквивалент после штатной подготовки отображения. |
| `pending` | Последний ожидающий снимок и Promise всей цепочки предшественников. До transaction complete он не является подтверждением. |
| `revision` | Счётчик уведомлений `saveSoon()` об изменении, не доказательство записи. |
| `sequence` | Порядок отличающихся запросов snapshot; одинаковый хвост переиспользует Promise. |
| `confirmed` | Sequence последнего фактического успешного `put`; 0 также служит исходной точкой после подтверждённого чтения. |
| `error` | Последний отказ, сохраняемый при изменениях и переключении контекста до успешной записи либо явной сверки с уже подтверждённым снимком. |

Перед созданием транзакции снимок ждёт своего предшественника. После ожидания
повторно проверяются workspace seal, удаление проекта и принадлежность состояния
существующему поколению map. Сравнение с `saved` выполняется после предшественника:
**A → B → A** нельзя пропустить только потому, что A когда-то было записано.
Одинаковые ожидающие снимки разделяют Promise; одинаковый уже подтверждённый
снимок обходится без новой транзакции. После ошибки новый flush может повторить запись.

`dbOp` и `runStoreRequest` по-прежнему подтверждают только `transaction.oncomplete`.
Только после этого обновляются `app.docs`, `saved` и `confirmed`. Старое подтверждение
не выдаётся за актуальную модель: индикатор сравнивает полный текущий снимок и
учитывает ожидающий хвост. Ошибка старой вкладки не записывается в состояние новой.

`setDoc` устанавливает эквивалентность только если **вход до подготовки** совпадал
с подтверждённой строкой `app.docs` и отсутствуют ожидающая запись и ошибка.
Сам `app.docs` хранит исходную подтверждённую запись, включая отсутствующие старые
поля. Новый документ без такой строки сохраняется как прежде. При пассивном flush
проверка равенства выполняется до save-time синхронизации, поэтому подготовка
отображения и автоматическое имя не становятся миграцией. Реальная правка проходит
обычные boundary/slide/title sync и сохраняет нормализованное содержимое.

`commit` сохраняет существующую историю, выделение и Undo/Redo; совпадающий с
подтверждённым/ожидающим снимком документ не получает новый timestamp только от
завершения операции. Live text input обновляет индикатор, запись завершается
существующим путём commit/передачи контекста.

Переименование использует последнюю модель открытой вкладки и тот же FIFO.
Имя в памяти меняется до await: следующая правка уже включает его. При отказе
память и ошибка остаются доступны для повторной попытки, `app.docs` не изменяется.

## Вкладки, серии и барьеры

- `captureDocumentTab()` завершает текст и raster stroke, синхронно захватывает
  снимок исходной вкладки до передачи `app.doc` и очищает её debounce. Его
  fire-and-forget Promise не является подтверждением закрытия: исходы находятся
  в состоянии конкретного документа, close/ZIP по-прежнему ожидают и проверяют их.
- Restore не уничтожает память неактивной вкладки и показывает её собственную ошибку.
- Close ждёт подтверждения и проверяет, не изменился ли снимок за время await;
  failure или history preview оставляют вкладку открытой.
- Повторный выбор холста сохраняет zoom/focus/scroll UX, не создавая save intent.
  Реальная смена индекса сохраняет корневое зеркало и `slides[activeSlideIndex]`,
  не создаёт шаг Undo только ради навигации. Рендер миниатюр не запускает сохранение.
- `workspaceBarrier` отслеживает **всю очередь**, включая снимки, ещё не дошедшие
  до IndexedDB. Сохраняются sticky errors остальных stores, Web Locks, заморозка
  workspace, drain перед удалением проекта и атомарная замена workspace.
- ZIP продолжает завершать ввод, проверять активную и неактивные вкладки, ждать
  очередь и читать согласованный readonly-снимок четырёх stores. Отказ не становится
  якобы завершённым состоянием архива. Чистый ZIP проверяется без новых `docs.put`.

## Измерения реальных IndexedDB операций

Обёртки тестов считают `IDBDatabase.transaction`, `put/add/delete`, commit и abort
с отдельными именами `docs`, `projects`, `fonts`, `settings`. Задержки удерживают
настоящую Chromium-транзакцию через get-запросы; abort выполняется после request
success. Результаты считываются readonly после complete и проверяются после reload.

| Воспроизводимый сценарий | До: `docs` readwrite / put | После |
| --- | ---: | ---: |
| Только загрузка уже сохранённого документа | 1 / 1 | 0 / 0 |
| Загрузка → открытие → главная → повторное открытие → закрытие → открытие | 5 / 5 | 0 / 0 |
| 8 переходов между двумя/тремя чистыми вкладками, fit, главная | 8 / 8 | 0 / 0 |
| Повторное нажатие активного холста | 1 / 1 | 0 / 0 |
| Повторное нажатие и реальная смена слайда | 2 / 2 | 1 / 1 |
| Старый документ: загрузка → открытие → главная | 3 / 3, запись изменена | 0 / 0, исходная запись сохранена |

Новая запись и реальное редактирование продолжают выполнять необходимый `put`.
A → A во время удержания выполняет одну транзакцию. A → B → C, изменение во время
записи, два изменения до debounce и ошибка → retry проверяются вместе с конечными
данными; уменьшение количества транзакций не подменяет проверку содержимого.
`projects.exportCounters` и записи других stores не оптимизируются.

## Регресс и границы

Новые проверки: **12 unit и 14 browser**. Полный локальный регресс и GitHub Actions
указаны в PR после завершения прогонов. Отдельно выполнялись существующие
`indexeddb-contracts`, `render-readonly`, `core-contracts`; ZIP и workspace suites
также входят в полный Playwright.

IndexedDB v3, JSON/ZIP, transaction complete, Web Locks и replacement-протокол,
cloud/OAuth, порядок рендера/PNG и исторические эталоны не меняются.
Подтверждение означает завершённую IndexedDB-транзакцию в этой сессии, а не гарантию
завершения async-кода после принудительного закрытия браузера. Конкурентные редакторы
в разных окнах сохраняют существующий instance/workspace-протокол; FIFO относится
к одному экземпляру. Автоматический retry после отказа не добавлен: повторный flush
или последующая правка могут инициировать новую попытку.
