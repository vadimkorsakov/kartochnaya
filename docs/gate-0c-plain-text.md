# Gate 0C/3 и 3B: plain-text WYSIWYG и legacy baseline Arial

3B продолжает Draft PR #76 от `47aea9bd32f8eb48d8744e4ad2a9159319a81c6a`.
Реализованные ввод, `applyTextStyle()`, preview, inline/document history и
сохранение сохраняются. Новая часть ограничена геометрией перехода plain→rich.

## Поддерживаемые случаи

С URL-флагом `?experimentalTextWysiwyg=1` обычный **Arial 32, normal/400,
lineHeight 1.15**, без runs, теперь сразу открывается в WYSIWYG:

- `ABCD` в достаточной по ширине рамке;
- `ABCD\nABCD`: две непустые строки с явным LF;
- первое частичное изменение цвета `[1,3)` сохраняет baseline и размер строки;
- сохранение, JSON, IndexedDB, reload и PNG используют тот же режим.

Допуск остаётся проверкой фактической геометрии установленного браузера.
Сильный kerning (например, Arial `AV`), тесные рамки, автоматические переносы
нового режима, различающиеся метрики параграфов, пустые строки и смешанная
типографика нового режима используют legacy textarea. Изменение шрифта/размера
в этом режиме передаётся существующему textarea; такая частичная правка тоже
сохраняет режим в существующем снимке истории. Первое оформление всей строки
не создаёт режим частичного перехода и использует прежний handoff.

Nimbus Sans 26 / lineHeight 1.03 продолжает работать без нового признака.
Прежнее исключение Nimbus Sans 32 в Firefox не расширено. URL-флаг, desktop
Chromium/Firefox, left/top, разрешённые загруженные шрифты и ограничения auto-fit,
масок, эффектов, вращения, vertical/path, mobile и CR/CRLF сохранены.
Порог `plainWysiwygLayoutCompatible()` остаётся **0.5 document px**.
Guard парных advances и запас ширины для двух границ диапазона не удалены.

## Почему необходим один признак

Существующий rich-документ Arial 32 с sparse цветом `[1,3)` должен оставаться на
baseline 29.4, а новый переход из plain-текста с теми же полями — на 24.828125.
Без дополнительного признака эти сохранённые слои неразличимы. Замена baseline
у всех rich-документов нарушила бы совместимость и PNG.

Используется ровно один необязательный признак слоя:

```json
"textLayoutMode": "legacy-top"
```

Он появляется только при первом реальном **частичном** оформлении подходящего
plain-слоя, когда обычная rich-раскладка требует вертикальной коррекции.
Открытие, выделение, курсор, no-op оформление и обычный ввод не записывают ни
этот признак, ни фиктивные runs, ни `textRunsBaseFontSize`. В памяти может
использоваться виртуальная проекция с режимом; исходный слой не меняется.

Первый цвет `#11aa33` для `[1,3)` в `ABCD` добавляет только:

```json
{
  "textRuns": [{"start":1,"end":3,"style":{"textColor":"#11aa33"}}],
  "textLayoutMode": "legacy-top"
}
```

`text` остаётся `ABCD`, остальные символы наследуют слой. Undo первого действия
удаляет и runs, и mode; Redo возвращает их. Escape восстанавливает весь исходный
слой. Document Undo/Redo после закрытия проверены отдельно. Явная полная очистка
оформления удаляет режим вместе с runs/reference size. Схема IndexedDB,
JSON-контейнер `kartochnaya-v1` и версия базы не менялись; новые данные проходят
через существующие копии JSON-слоёв без миграции. Старые сборки, не знающие
признак, не гарантируют геометрию новых marked-документов.

## Раскладка

Для каждого полного текста строки измеряются тем же Canvas-контекстом:

```text
legacyAlphabeticY = topY + actualAscent(alphabetic) - actualAscent(top)
```

В `legacy-top` Canvas/PNG используют этот baseline и legacy line step. Полный
текст строки измеряется также после разделения цветом, чтобы набор отдельных
фрагментов не менял базовую линию. В ключ кэша раскладки включён режим.
Без `legacy-top` формулы старого rich-layout остаются прежними. Unit-проверка
попеременно запрашивает оба режима одного документа и проверяет изоляцию кэша.

DOM не предполагает равенства CSS baseline и Canvas fontBoundingBox baseline.
Перед проекцией невидимый inline-probe измеряет реальный CSS baseline; только
тогда span получает относительное вертикальное смещение. Это не меняет x/y/w/h
слоя или host. Старые unmarked rich-сессии не используют этот probe/смещение,
включая их переход к пустому тексту. Native Selection/UTF-16 mapping не менялись.

## Измерения single-line и LF

Для Arial 32 в Chromium:

| Геометрия | До 3B | После 3B, включая первый цвет |
| --- | --- | --- |
| legacy Canvas baseline первой строки | 24.828125 | 24.828125 |
| Canvas rich baseline первой строки | 29.4 | 24.828125 только с `legacy-top` |
| Canvas baseline второй строки | legacy 61.628125 / rich 66.2 | 61.628125 |
| Canvas line step | 36.8 в обоих алгоритмах | 36.8 |

Исходный скачок `+4.571875 document px` был расхождением baseline, а не высоты
строки. После первого цвета **Δ Canvas/PNG = 0**. В Firefox измеренный legacy
baseline около `24.8241415193`; используется именно он, а не константа Chromium.

Измерение DOM baseline выполняется нулевым inline baseline-probe, а не допущением,
что верх DOM Range плюс fontBoundingBoxAscent уже равен baseline. Дополнительно
проверяются реальные прямоугольники каждого символа и native collapsed Range.
Следующие Δ относительно legacy Canvas одинаковы **до и после цвета**:

| Browser / zoom | Δ DOM baseline, строка 1 | Δ DOM baseline, строка 2 | Максимальный Δ x/width символов |
| --- | ---: | ---: | ---: |
| Chromium 50/100/200% | 0 | −0.003125 | 0 |
| Firefox 50% | +0.0092325042 | +0.0091592620 | 0.0166988373 |
| Firefox 100% | −0.0074911286 | −0.0074423005 | 0.0000247956 |
| Firefox 200% | −0.0074911286 | −0.0074728181 | 0.0000152588 |

Все величины таблицы — document px. Browser-тесты ограничивают расхождение
Arial DOM/Canvas величиной **0.05 px**, не расширяя основной guard 0.5 px.
Неизменённое закрытие также сравнивает точные Canvas-пиксели без PNG-эталонов.
После первого цвета native Canvas-вызовы, включая PNG export после reload,
совпадают по координатам, метрикам и baseline.

В Chromium дополнительно снимается **реально нарисованная native-каретка**:
на время теста меняется только её цвет, затем пиксели сопоставляются с collapsed
Range. Максимальное расхождение края — 1.375 screen px на 200% из-за native
растеризации/округления caret до transform; вертикальное — не более 0.828125
screen px. Положение не меняется при первом цвете.

**Ограничение Firefox-проверки:** Playwright Firefox screenshot не показывает
native-каретку даже в изолированном обычном `contenteditable` без приложения,
на 50/100/200%, включая отключение blink. Поэтому Firefox проверяет native
Selection/collapsed Range, baseline и glyph Range, но не заявляет проверку
растровой каретки. Тест не рисует искусственную каретку и не подменяет baseline.
Результаты и этот статус записываются в `arial-legacy-top.json` attachments.

## Совместимость и проверки

Старый unmarked Arial rich-документ проверен на прежних baseline 29.4 / 66.2,
точных Canvas-пикселях после no-op и прежней PNG-геометрии. Оба Canvas-алгоритма
не объединены, `usesRichTextLayout()` не заменён глобальным true. Строгие verdict
Gate 0A/0B не изменены. Mobile UI, auto-fit, rotation, IME, CRLF, эффекты,
облачные функции и механизмы ввода/истории/сохранения не переработаны.

- Chromium: **89 passed**, целевые `inline-wysiwyg`, `rich-text`, `inline-text`,
  `rich-text-rendering`.
- Firefox smoke: **18 passed**.
- `npm run test:source` — passed; `npm run test:unit` — **16 passed**.
- `npm run build` — passed; `git diff --check` — passed.
- Полный `test:all` не запускался; PNG-baselines не менялись.

PR #76 остаётся Draft. Merge, Production Deploy и перевод в Ready не выполняются.
После push GitHub Actions проверяются один раз без ожидания и повторного опроса.
