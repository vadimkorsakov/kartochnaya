## Прежняя зависимость и границы изменений

`core/gradient-model.js` был фрагментом без import/export. Сборщик проверял
маркер `/*{{KARTOCHNAYA:CORE_GRADIENT_MODEL_JS}}*/` и вставлял текст между
`hexAlpha` и `getGradientStop` внутри strict IIFE редактора. Четыре function
declarations использовали его лексические зависимости и hoisting.

Теперь `src/core/gradient-model.mjs` экспортирует только
`createGradientModel(uid)`. Она возвращает `gradientStops`, `gradientGeometry`,
`gradientSample`, `addGradientStop`. Тела всех четырёх функций, включая пробелы,
сохранены буквально: source-тест сравнивает их с историческим HTML.

На уровне модуля импортируются `clamp` из `./primitives.mjs` и
`normalizeHex`, `hexRgb`, `rgbHex` из `./colors.mjs`. Остальные используемые API —
стандартные `Array`, `Number`, `Math`. Модель не использует DOM, IndexedDB,
`window`, `globalThis`, приложение или реестр сервисов. Runtime-зависимостей,
валидации генератора, новой обработки ошибок и новых алгоритмов не добавлено.

`editor.js` изменён только в трёх местах: импорт фабрики; одна строка создания
экземпляра; удаление старого маркера. Остальная программа, включая `app`,
`uid`, Canvas, pointer/touch, клавиатуру, слои, историю, сохранение, текстовые
обёртки и повторные объявления, защищена побайтовым сравнением исходника.
CSS, HTML-шаблон, manifest, service worker, иконки и формат документов не менялись.

## Передача uid и порядок инициализации

Существующая строка генератора остаётся в IIFE без изменений:

```js
const uid=()=>globalThis.crypto?.randomUUID?.()||('id-'+Date.now()+'-'+Math.random().toString(36).slice(2));
const { gradientStops, gradientGeometry, gradientSample, addGradientStop } = createGradientModel(uid);
```

Фабрика создаётся сразу после объявления `uid`, до `clone`, каталога фигур,
`app`, регистрации событий и `init()`. Перед ней выполняется только создание
DOM-селекторов и самого генератора; вызовов модели здесь нет. Фабрика лишь
создаёт функции и возвращает объект: не вызывает `uid` и не читает данные
редактора. Это проверяется unit-тестом с генератором, выбрасывающим ошибку при
вызове, и source-проверкой положения binding. Импорты ацикличны и не запускают
приложение. TDZ между объявлением генератора и созданием модели отсутствует.

Раньше объявления модели поднимались внутри IIFE. Теперь её локальные имена
доступны после второй строки, ещё до любой остальной инициализации. Таким
образом, ранний путь не зависит от прежней позиции текстового маркера.
`init()` остаётся на исторической позиции; `await openDB()` и порядок установки
поздних обёрток не изменены. Глобальных обходов или production-hooks нет.

И редактор, и фабрика получают одну и ту же функцию `uid`, а не копию её
реализации. У каждой фабрики собственное замыкание. Модель не имеет изменяемого
состояния уровня модуля и не создаёт дополнительных ID при конструировании.

## Аудит потребителей и сохранённых контрактов

| Функция | Зависимости и мутации |
| --- | --- |
| `gradientStops(e)` | `uid`, `normalizeHex`, `clamp`; при отсутствии массива или длине <2 заменяет его двумя точками; иначе сохраняет массив и объекты. Назначает недостающие falsy ID по порядку обхода, нормализует поля и сортирует исходный массив на месте. Возвращает этот же массив. |
| `gradientGeometry(e)` | Стандартные `Number`/`Math`; при отсутствии любой конечной точки пересоздаёт обе, записывает нормализованные координаты. При повторном вызове сохраняет их ссылки, возвращая новые экранные координаты. ID не создаёт. |
| `gradientSample(e,pos)` | Вызывает `gradientStops`, поэтому может создавать/нормализовать/сортировать точки; использует `clamp`, `hexRgb`, `rgbHex`. Прежние формулы RGB/alpha, крайние и некорректные значения сохранены. |
| `addGradientStop(e,pos=50)` | Сначала sample, затем один `uid`, прежнее округление позиции и alpha; push в исходный массив и повторная нормализация/сортировка. Возвращает тот же новый объект, который находится в массиве. |

При `addGradientStop({})` первые два `uid` вызываются до присвоения нового
массива, третий — после sample, но до push новой точки. Это проверяется снимками
входного объекта непосредственно в переданном генераторе. Относительный порядок
мутаций и запросов ID сохранён, в том числе при ошибках и повторной нормализации.
Историческая особенность uppercase короткого HEX и его последующего приведения
к lowercase остаётся контрактом, а не исправляется.

Потребители сохраняют локальные имена и алгоритмы:

- `getGradientStop`, `gradientCSS`, `gradientStopsUI` читают и нормализуют точки;
  выбранная остановка по-прежнему определяется сохранённым ID.
- `gradientScreenPosition`, overlay, hit-testing, проекция позиции на линию,
  геометрические ручки и `fillPaint` используют прежние координаты и точки.
- Палитра, `changeGradientStop`, pointer-обработчики шкалы и Canvas, добавление,
  удаление и перемещение остановок не переписаны.
- `commit`, snapshot/Undo/Redo, `saveSoon`, `flushSave`, JSON-экспорт и `setDoc`
  сохраняют и открывают прежние структуры. Миграции данных не требуется.

## Текущая структура JavaScript и сборка

```text
editor.js (прежний strict IIFE, импортирует фабрику и helpers)
  ├─ core/primitives.mjs
  ├─ core/colors.mjs → primitives.mjs
  └─ core/gradient-model.mjs → primitives.mjs + colors.mjs
       └─ createGradientModel(uid из IIFE)
```

`gradientModelSlot` и `assembleLegacyJavaScript()` удалены. Старого `.js` нет.
`compile-javascript.mjs` использует обычный `entryPoints: ['editor.js']` с
`absWorkingDir`, указывающим на актуальную директорию исходников. Текстовых
JavaScript-подстановок больше нет. HTML/CSS по-прежнему вставляются штатным
`compile-html.mjs` в неизменённый шаблон.

Сохранены esbuild **0.28.2**, `bundle: true`, `platform: 'browser'`,
`format: 'iife'`, `target: 'es2022'`, `minify: false`, `treeShaking: false`,
`sourcemap: false`, UTF-8, strict banner и защита `inline-script`.
Проверяются предупреждения, единственный output, отсутствие runtime-импортов
в metafile, динамических импортов и сырого закрытия inline-script. Результат
парсится Node VM как классический скрипт, без исполнения приложения.

Дополнительно читаются реальные inputs из metafile: неразрешённый маркер
отклоняется даже в комментарии, который esbuild мог бы удалить. Это чтение для
проверки, а не подстановка кода. Отсутствие модуля, неверный путь/экспорт и
синтаксические ошибки прерывают сборку; исторический HTML не используется как
fallback. Проверки отказов выполняются во временных копиях исходников.

HTML содержит один встроенный классический скрипт. Внешние JS/MJS, CDN и
`type="module"` не нужны. ZIP содержит этот же HTML под именем `index.html` и
17 прежних runtime-ресурсов. Детерминированный STORE ZIP, состав и метаданные
не менялись. `build:verify` не ослаблен и проверяет байты реальных ZIP entries.

## Workflow, ограничения и откат

Существующий **Build HTML and PWA** не изменён. Он уже запускается для PR в main,
а `src/**` включён в фильтры push. Порядок сохранён: npm ci → source → unit →
build → verify → установка Chromium → bundle smoke → загрузка двух артефактов.
Серверный результат проверяется после открытия PR и сообщается отдельно;
локальный прогон не является подтверждением GitHub Actions.

Редактор остаётся большим IIFE; фабрика выделяет только математическую модель.
Ссылочные мутации, историческая нормализация и повторные объявления намеренно
сохранены. KF-001, KF-002, KF-003 и ENV-001 не исправляются. Автономный `file://`
локально не подтверждён из-за административной блокировки Chromium; HTTP и
офлайн-PWA прошли. Firefox/Windows этапа 7, Safari, реальные touch-устройства
не проверялись. Проверка этапа 6 владельцем не заменяет эти проверки.

До merge достаточно закрыть PR; main и пользовательские данные не изменены.
Для отдельной диагностики этапа 6 используйте отдельную рабочую копию на
`926640b72c837f96018369325170bd7e84973623` и штатные npm-команды. После возможного
merge откатывайте весь коммит этапа 7 отдельным revert-PR; для merge-коммита
нужен `git revert -m 1 <merge-коммит-этапа-7>`. Вместе возвращаются фабрика,
подключение редактора, сборщик и тесты; заново выполняются source/unit/build/verify
и браузерные проверки. Не меняйте данные IndexedDB или эталоны ради отката.
Не подставляйте старый HTML при ошибке актуальной сборки.

Этап 8 требует отдельного задания. Рекомендуется начать с аудита следующей
небольшой подсистемы: явные зависимости, ранние вызовы, мутации и существующие
пользовательские контракты. Не переносить uid, Canvas, историю или все текстовые
обёртки автоматически вслед за этой фабрикой. Сохранить новый граф импортов и
полученные проверки как границу дальнейшей миграции.
