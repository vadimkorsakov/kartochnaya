# Яндекс Диск: ZIP-бэкапы 15В-1

База: `8e17076a49b49b91a821220d8d0550b370f8a2e9`.

`client.mjs` получает OAuth-сеанс, функции подтверждённого снимка и чтения
preferences. Он не открывает IndexedDB и не читает состояние редактора.
Netlify передаёт существующую `zipSavedSnapshot`: ожидание операций редактора,
подтверждение сохранений всех вкладок и согласованный readonly-снимок IndexedDB v3.
Ошибка сохранения прекращает создание до запроса ссылки загрузки.

Используется существующий `createBackup` и формат `kartochnaya-backup-v1`:
manifest.json, UUID backupId, дата, SHA-256 записей, проекты/документы/ресурсы,
шрифты, settings и предусмотренные форматом preferences. Выборочных копий нет.
Имя берётся из архиватора: `kartochnaya-<timestamp>-<backupId>.zip`.
Ни названия проектов, ни OAuth-данные в путь не входят.
Формат, IndexedDB и автономные HTML/PWA ZIP не изменяются: импорт облачного UI
и передача snapshot выполняются только трансформацией Netlify.

## Разрешения и API

Scope остаётся `cloud_api:disk.app_folder`. Архивы находятся в корне папки
приложения Яндекс Диска (`app:/`, в интерфейсе Диска — папка приложения).
OAuth allowlist разрешает только:

- GET `https://login.yandex.ru/info` — устойчивый ID, только в памяти сеанса;
- GET `/v1/disk/resources?path=app:/`, необязательные limit 1–100 и offset 0–10000;
- GET `/v1/disk/resources/upload?path=app:/<ZIP>&overwrite=false`;
- GET `/v1/disk/resources?path=app:/<ZIP>` — подтверждение файла;
- прежние GET upload/download и DELETE permanently=true для диагностического
  `kartochnaya-probe-<43 Base64URL символа>.txt`.

Имена ZIP проверяются целиком: фиксированный timestamp архиватора и UUID,
строчное `.zip`, никаких подкаталогов, traversal, вложенного URL-кодирования,
произвольных имён, повторных или лишних параметров. Запросы к `disk:/`,
публикация, права, overwrite, DELETE ZIP, сторонние API запрещены.
Ответ метаданных может содержать канонический `disk:/…`: он принимается только
как прямой дочерний путь папки, полученной запросом `app:/`. Запросов к этому
каноническому пути нет. Из ответа сохраняется только явная проекция метаданных.
Имена отображаются через textContent.

## Размер, передача и подтверждение

Сохраняется лимит архиватора 512 МиБ исходных данных. Дополнительный предел
готового ZIP до сети: 256 МиБ desktop и 128 МиБ Android (как политика Drive).
В PUT передаётся исходный Uint8Array; полной дополнительной копии для Blob нет.
Общий срок операции ограничен 15 минутами, подписанный PUT — 10 минутами.
Обычные API и диагностика сохраняют предел 30 секунд, OAuth — 120 секунд.
Кнопка отмены прекращает ожидание/сеть; при подготовке архиватор завершает свою
текущую работу, но отменённая операция не сможет отправить ZIP.

Upload-link проверяется по HTTP, method=PUT, templated отсутствует/false и
существующему allowlist подписанных хостов (он не расширен). PUT использует
Content-Type application/zip, credentials=omit, redirect=error, cache=no-store,
mode=cors, referrerPolicy=no-referrer, без Authorization. Только диагностический
подписанный GET сохраняет redirect=follow и проверку конечного хоста.
Успех PUT 201/202 сам по себе ещё не означает «Копия создана».

Подтверждение читает метаданные именно нового имени: type=file, точный путь,
имя, размер, корректная дата; если сервер предоставляет SHA-256, он сравнивается
с локальным SHA-256 всего ZIP. При наличии только размера UI прямо сообщает,
что побайтовая проверка не выполнялась. При HTTP 404 разрешены четыре чтения
метаданных с интервалами 0.5/1/1.5 секунды. PUT никогда не повторяется автоматически.
Содержимое облачных ZIP на этом этапе не скачивается.

При сетевом отказе, отмене PUT, неподтверждённых метаданных или расхождении:
«Загрузка не подтверждена. Файл мог сохраниться на Диске. Обнови список копий».
ZIP не удаляется, перезаписи нет. Обновление списка не повторяет PUT. Новый ZIP
можно отправить только новым явным нажатием кнопки создания, с новым UUID/именем.

## Список и сеанс

Список запрашивает только метаданные, по 100 элементов (последняя страница может
быть меньше), до 1000 элементов всей папки, включая посторонние файлы.
При превышении показывается явное сообщение об усечении. Повреждённая пагинация
и HTTP-ошибки показываются ошибками, а не пустой папкой. Подходящие файлы
фильтруются по имени, прямому пути, type=file и корректным метаданным; новые
сначала. UI использует существующий pager по четыре записи. «Доступен» означает
наличие серверных метаданных, не результат скачивания или проверки manifest.

Одна активная сессия, без мультиаккаунтности. Поколение OAuth защищает всю
длительную подготовку и передачу. /info проверяется до/после подготовки и перед
выдачей результата/списка. Если ранее известный ID изменился или перестал
подтверждаться, требуется повторное подключение. Если /info изначально недоступен,
ID остаётся неизвестным; данные прежнего поколения не используются. В таком
режиме изоляцию обеспечивает действующий токен и поколение сеанса.
Отключение, expiry, Client ID, новая авторизация, pagehide/reload очищают список,
сбрасывают ID и отменяют операции. Поздние результаты старой операции UI игнорирует.
Закрытие модального окна сохраняет подключение и статус. Ошибка операции видна
на любой вкладке. OAuth access/refresh tokens, capability URL и ID аккаунта
не сохраняются в localStorage, IndexedDB, ZIP или логах; только публичный Client ID
может сохраняться в localStorage.

## Ручная проверка Deploy Preview

1. Открыть Deploy Preview в Firefox, зарегистрировать точный callback URI preview
   в приложении Яндекс OAuth; разрешение только app_folder. Создать документы
   в нескольких проектах, добавить ресурс/шрифт, проверить сохранение.
2. «Данные → Яндекс Диск → Подключение»: настроить Client ID, подключиться.
   Проверить четыре вкладки и подключённый статус; закрыть и открыть окно.
3. «Создать копию»: создать ZIP. Наблюдать подготовку, PUT, подтверждение.
   В Network проверить overwrite=false, отсутствие Authorization/cookies на PUT,
   реальный ZIP и отсутствие POST/DELETE пользовательского архива. Не публиковать
   токены, подписанные URL или HAR с секретами.
4. «Облачные копии»: обновить; проверить имя, дату, размер, тип, новые сначала,
   пагинацию, отсутствие diagnostic TXT. При размере без SHA не должно быть
   заявления о побайтовой проверке. Создать вторую копию — имя должно отличаться.
5. Отменить медленный PUT: успех не показывается, повторного PUT/удаления нет.
   Обновить список, проверить возможный сохранённый файл. Проверить отключение
   во время подготовки и повторное подключение другого аккаунта: старый список
   не появляется. Reload требует подключения заново.
6. Повторить на Firefox Android. Проверить переносы имён и статусов, отмену,
   сохранность документов после копирования; выполнить прежнюю диагностику
   и отдельно удалить её тестовый TXT.

Успешные mocks не заменяют живую проверку Firefox. Живая передача ZIP этого
этапа проверяется отдельно в Deploy Preview перед следующим этапом.
Merge выполняет пользователь после успешной автоматической регрессии.
Production Deploy в рамках задачи не выполняется.

Ограничения: нет скачивания/восстановления ZIP, ротации/удаления архивов,
автоматизации, синхронизации, серверного proxy или новых OAuth-разрешений.
