## Исходный аудит и граф зависимостей

До этапа `importProjectBackup` записывал проект, каждый документ и каждый шрифт
отдельными транзакциями. `importWorkspaceBackup` повторял это для каждого проекта.
Каталог фигур применялся ещё до проверки архива, в том числе в `importJSON` перед
диспетчеризацией формата. `deleteProject` сначала закрывал вкладки с записью их
снимков, затем удалял документы из `app.docs`, проект и отдельно создавал замену.
Отказ мог оставить часть данных, а закрытые вкладки уже нельзя было восстановить.

Вставка ресурса в документ копирует изображение в слой; удаление исходного ресурса
не является каскадным удалением его изображений в документах. Фигуры/шрифты глобальны
и не удаляются с проектом, поскольку могут использоваться другими проектами.

## Чистая модель и диагностика

`src/model/project-integrity.mjs` экспортирует две функции:

- `analyzeProject(project, documents = [])` возвращает `{errors, warnings, info}`.
- `prepareProjectImport(items, options)` принимает `[{project, documents}]`,
  `generateId`, `now`, занятые внешние ID и лимиты; возвращает
  `{projects, documents, diagnostics}` либо бросает ошибку с `.diagnostics`.

Функции не обращаются к редактору, DOM, Canvas, storage и сети. Каждый элемент
диагностики имеет стабильные `code` и `path`, для workspace — с индексом проекта.
Анализ не исправляет и не изменяет входные данные. Подготовка делает независимые
глубокие JSON-копии, сохраняя неизвестные свойства. Поддерживаются JSON-архивы
прежних форматов, новая схема/формат не вводятся.

Критические ошибки: неверный объект/список, невалидный холст, принадлежность другому
проекту, дубли внешних ID в архиве, дубли ID папок/ресурсов/элементов/групп в их
областях, циклы папок, повреждённые слайды. Проверяются корневые холсты и каждый
слайд, размеры в диапазоне `(0, 5000]`, уникальность ID слайдов. Одинаковые локальные
ID разных документов допустимы. Обход дерева итеративный, тестируется глубина 10000.

Отсутствие исторических необязательных полей (`resourceFolders`, `resources`,
`groups`, документного `projectId`) — информационная диагностика. Старый внешний ID
может отсутствовать: новый генерируется в плане. Ссылки на отсутствующие папки,
группы, clip-base или boundary и невалидный индекс активного слайда дают
предупреждения. Такие записи сохраняются целиком: импорт показывает число
предупреждений и пишет структурированную диагностику в консоль. Папка с произвольным
именем не создаётся, данные не удаляются. Это сознательная совместимость с
историческими неполными архивами, а не автоматический ремонт.

Для каждого проекта/документа `generateId` вызывается до транзакции. Пустое значение,
коллизия с существующими или исходными внешними ID и повтор уже выданного ID
отклоняются. В редакторе используется существующий `uid` (crypto.randomUUID с прежним
fallback). `documents[].projectId` заменяется ровно на ID новой записи-владельца.
Внутренние ID слоёв, групп, масок, слайдов и ресурсов остаются прежними.
Новые ID не публикуются в `app` до commit. Время передаётся параметром для
детерминированных тестов. Исходные пользовательские записи не переписываются.

## Минимальный multi-store API

```js
await runStoreTransaction(db, ['projects', 'docs'], 'readwrite', store => {
  store('projects').add(project);
  for (const document of documents) store('docs').add(document);
});
```

Callback синхронно ставит запросы в одну транзакцию и возвращает `undefined`.
Асинхронная функция отклоняется до вызова; возвращённый Promise/thenable/IDBRequest
или любое другое значение нарушает контракт и приводит к abort. Запрещены `await`,
FileReader, fetch, таймеры и пользовательские подтверждения в callback.
Для зависимых запросов допустимы синхронные обработчики IDBRequest той же транзакции.

Promise разрешается только в `transaction.oncomplete`; request success остаётся
предварительным. `onerror`/`onabort` отклоняют операцию. Первая исходная причина
ошибки сохраняется, ошибки запросов не подавляются через preventDefault. Исключение
callback отменяет транзакцию. Неизвестный store, закрытая/недоступная база, неверный
callback и некорректный набор store отклоняются. Существующие `runStoreRequest` и
`openDatabase` сохранены побайтово, включая прежний readonly fallback.

## Импорт проекта и рабочего пространства

`importProjectBackup` и `importWorkspaceBackup` используют один `importProjectSet`:

1. Чистая проверка всех проектов/документов/папок и подготовка внешних ID.
2. Предварительная проверка каталога фигур; `flushSave` защищает активный документ.
3. Подготовка итогового набора шрифтов: нормализация копий, пропуск дублей,
   загрузка FontFace без регистрации. Нет data — предупреждение; неподдерживаемый
   шрифт — диагностируемый пропуск; дубликат family/weight/style — info.
4. Проверка сохранности пользовательского контекста.
5. Одна readwrite-транзакция `projects` + `docs`, с `fonts` и `settings` только
   при наличии принятых записей. Для новых ID используется `add`, чтобы коллизия
   не перезаписала чужую запись. Каталог использует `put` по прежнему ключу.
6. Только после oncomplete публикуются проекты, документы и шрифты, регистрируются
   загруженные FontFace и применяется каталог. Выбор проекта/документа меняется
   только при совпадении сохранённого контекста, затем обновляется библиотека.
   Документ выбирается только из первого выбранного проекта. Если он пустой,
   выполняется переход на рабочее пространство с этим проектом; прежние вкладки
   сохраняются, документы других импортированных проектов автоматически не открываются.

Один workspace — одна транзакция на все проекты. Невалидный последний проект
выявляется до начала записи; ошибка записи последнего документа откатывает все
новые проекты и документы. Лимиты прежние: 2000 документов отдельного проекта,
500 проектов/5000 документов workspace; холст не больше 5000 px. Произвольного
предела размера JSON нет: общий барьер 50 MiB из первого коммита PR #12 удалён,
чтобы штатный экспорт с изображениями оставался пригодным для обратного импорта.
Файл по-прежнему читается через File.text и разбирается JSON.parse в существующем
try/catch. Фактические ограничения памяти браузера и IndexedDB остаются.

`importJSON` сначала направляет проект/workspace в атомарный путь, чтобы старое
предварительное применение shapeCatalog не меняло глобальные данные до импорта.
Алгоритм переназначения внутренних ссылок отдельного документа не изменён; KF-001
остаётся воспроизводимым.

При отказе в базу и `app` не попадают новые проекты/документы/глобальные записи,
успех не сообщается. Ранее открытый документ сохраняется. Подготовительный flush
может отдельно сохранить текущие пользовательские изменения — это намеренный
барьер до импортной транзакции. Уже сохранённые старые проекты и документы остаются.

FontFaceSet не транзакционен. Регистрация происходит после commit и сама по себе
не является частью гарантии IndexedDB; загрузка поддерживаемого шрифта заранее
проверена. При аварии страницы между commit и обновлением памяти данные читаются
при следующем запуске. Внешние сетевые ресурсы не скачиваются в новую систему
хранения и не получают гарантию доступности.

## Удаление, вкладки и конкуренция

После подтверждения `deleteProject` сохраняет активный документ через `flushSave`
и снимки открытых документов удаляемого проекта. Предпросмотр истории и отказ
сохранения прекращают удаление, сохраняя вкладки. Вкладки заранее не закрываются.

Затем ставится guard удаляемого проекта, очищается debounce и ожидаются ранее
выданные операции сохранения. В одной readwrite-транзакции `projects`/`docs`:

- удаляется проект;
- `projects.count()` после удаления определяет необходимость запасного проекта;
  `add` проекта «Мой проект» ставится из success-обработчика в ту же транзакцию;
- `docs.openCursor()` обходит реально сохранённые записи; для каждого совпадающего
  `projectId` вызывает `cursor.delete()` и продолжает курсор в той же транзакции.

Таким образом удаляются и исторические документы, которых нет в `app.docs`.
Чтение не отделено от удаления независимой транзакцией. При любой ошибке исходный
набор возвращает сама IndexedDB. Не используется компенсирующее восстановление.

После commit удаляются записи и вкладки из оперативных списков, обновляются activeId,
lastDocumentId, текущий документ, выбранный проект и библиотека. При abort эти
оперативные структуры не меняются. Глобальные шрифты и настройки не удаляются.

Небольшой guard сериализует импорт/удаление в одном экземпляре. Во время операции
capture-обработчик блокирует новые действия click/keydown/pointerdown/input/change/
drop, включая повторный импорт/удаление и переключение контекста. Перед применением
результата импорта дополнительно проверяются проект, документ, active tab и home.
Снимки удаляемого/успешно удалённого проекта больше не записываются через
`saveDocumentSnapshot`. `persistProject` также запрещает позднюю запись его старого
объекта (например, после завершения декодирования ресурса), предотвращая воскрешение.
Общий менеджер вкладок, история и Canvas не перестраивались.

Блокировка локальна одному экземпляру редактора. Другое окно может хранить устаревший
документ и позже снова записать его, сменить каталог или добавить данные после
завершения транзакции. IndexedDB сериализует конфликтующие транзакции, но не
синхронизирует `app` разных окон. BroadcastChannel, межоконная блокировка и облачная
синхронизация не добавлялись. Рекомендуется выполнять импорт/удаление в одном окне;
другие окна после этого перечитать. Старые асинхронные загрузчики файлов не превращены
в общий диспетчер: поздняя запись удалённого проекта отклоняется существующим путём
ошибки сохранения ресурса.

Новый `project-integrity-editor-diff.json` описывает семь точных блоков относительно
исходной main. Каждый содержит исходные строки, координаты и SHA-256 нового текста:

| Блок | Разрешённое изменение |
| --- | --- |
| imports | Импорт multi-store API и чистой модели |
| persistProject | Запрет поздней записи удаляемого/удалённого проекта |
| saveDocumentSnapshot | Запрет позднего автосохранения документов такого проекта |
| importProjectBackup/importProjectSet | Общая предварительная подготовка, guard, одна транзакция, публикация после commit |

Source-тест сначала точно обращает эти семь изменений и проверяет SHA всего
редактора этапа 10, затем применяет неизменённый старый манифест и сравнивает весь
оставшийся legacy-код с историческим исходником. Нет whitelist всего editor.js.
Отрицательные тесты проверяют изменения внутри каждого нового блока и вне блоков,
а прежние отрицательные проверки сохранены. Неизменённый префикс storage-модуля
защищён отдельным SHA. Защита всех прежних core-модулей, HTML/CSS, baseline-манифеста,
19 исторических файлов и PNG-эталонов сохранена. Новый модуль участвует в реальной
сборке, проверках отсутствующих файлов/маркеров/детерминизма и отсутствии runtime imports.

## Остаточные ограничения и откат

Завершение транзакции означает commit в модели IndexedDB, но не является гарантией
против очистки профиля, потери устройства, квоты/политики браузера, приватного режима
или отказа оборудования. Закрытие страницы до завершения записи не гарантирует
сохранение. Атомарность не охватывает app, localStorage, FontFaceSet или загрузки
файлов. Независимые подготовительные flushSave не откатываются вместе с импортом.
Большие изображения/шрифты могут расходовать память при подготовке JSON-копий.
Полная межоконная синхронизация отсутствует, глобальные fonts/settings остаются общими.

Схема не изменялась, поэтому откат к сборке исходной main читает те же записи.
Перед откатом экспортировать важные проекты прежним JSON-экспортом, закрыть лишние
окна, заменить HTML/PWA предыдущей сборкой и обновить приложение/кэш штатно. Проверить
проект и документы после открытия. Откат кода не восстанавливает уже успешно удалённые
данные; откат транзакции при ошибке происходит автоматически и не требует импорта.

Для будущего движка бэкапов рекомендуется повторно использовать чистый план и
структурированную диагностику, сохранять локальные ID внутри документов, готовить
бинарные данные/шрифты вне активной транзакции, определить отдельную политику
замены глобальных настроек и межоконной конкуренции, подтверждать только commit.
Сначала потребуется самостоятельный контракт состава/восстановления бэкапа.
Резервный менеджер, новый формат ZIP, восстановление всей базы, облачные подключения,
OAuth и синхронизация на этом этапе не реализуются.
