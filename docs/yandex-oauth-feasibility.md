# Яндекс Диск: OAuth PKCE и браузерный API (15Б)

Дата: 23 октября 2026. База: `d3d4b1a508d4bcea0778b382631454a1d94db19a`.
Это feasibility spike, без резервных копий, синхронизации и серверного посредника.

## Официальные контракты

**Подтверждено** по документации, просмотренной при подготовке PR:

- [OAuth Authorization Code + PKCE](https://yandex.ru/dev/id/doc/ru/codes/code-url):
  S256, state, force_confirm=yes, POST `/token` с form-urlencoded.
  Документ прямо разрешает не передавать client secret при наличии code_verifier.
  Поле scope в ответе необязательно; если оно есть, проверяется app_folder.
- [API Яндекс ID](https://yandex.ru/dev/id/doc/ru/user-information):
  `/info` принимает `Authorization: OAuth …`; базовые данные, включая устойчивый
  `id`, описаны и для токенов других сервисов. Это не гарантия CORS.
  ID проверяется только в памяти, в результаты и постоянное хранилище не попадает.
- [REST API Диска](https://yandex.ru/dev/disk/rest/),
  [актуальный раздел](https://yandex.ru/dev/disk-api/doc/ru/),
  [загрузка](https://yandex.com/dev/disk/api/reference/upload.html),
  [скачивание](https://yandex.com/dev/disk/api/reference/content.html):
  ссылки получают через resources/upload и resources/download, затем выполняют
  PUT/GET. PUT не требует OAuth-токена; ответ Link задаёт method и href.
  В примерах встречаются uploader…dst.yandex.net и downloader.dst.yandex.ru.
  Формулировка про токен скачивания в документации неоднозначна: вводный текст
  упоминает тот же токен, пример прямого GET не содержит Authorization.
  Прототип проверяет подписанный GET без OAuth-заголовка; при 401/403 остановится,
  автоматической пересылки токена на другой хост нет. Это отдельный вопрос живого опыта.

Запрашивается **только** `cloud_api:disk.app_folder`, пути только `app:/`.
Полный Диск и `GET /v1/disk` не запрашиваются. Фактические разрешения `/info`,
метаданных папки, upload/download/delete проверяются отдельно.
Никакие дополнительные scope при отказе не добавляются.

## Redirect URI и запуск

Для production-origin, указанного в существующей документации проекта, точный URI:

`https://kartochnaya.netlify.app/oauth/yandex-callback.html`

Для Deploy Preview нужен **его собственный** origin плюс
`/oauth/yandex-callback.html`, с точным совпадением в настройках Yandex OAuth.
Диалог «Настроить Client ID» показывает фактический URI текущего origin.
Production-деплой этого PR ещё не выполнялся, merge не выполняется.

Настроить приложение Яндекс OAuth с публичным Client ID и единственным scope выше.
Открыть на Netlify «Данные» → «Яндекс Диск · проверка подключения».
После настройки нажать «Подключить Яндекс»: popup открывается синхронно из click,
до асинхронного SHA-256. Verifier и state независимы, по 256 бит случайности;
verifier содержит 43 символа Base64URL. Попытка ограничена 120 секундами,
API-операция — 30 секундами. Отключение, уход со страницы, отсутствие сети и
истечение токена сбрасывают сессию и отменяют запросы.

Mock-тесты и Node.js не подтверждают реальный CORS. В PR нет заявления об успешном
живом OAuth. Браузерный fetch обычно не различает CORS, сеть и запрещённый redirect:
диагностика указывает шаг и неопределённость, HTTP-код — только если ответ доступен.
Недоступность ответа не доказывает неверный authorization code. HTTP 403 сам по себе
также не доказывает отсутствие scope.

## Ручной сценарий: Netlify, Firefox desktop и Android

1. Развернуть ветку как Netlify preview. Убедиться, что callback выдаёт отдельный
   HTML, статус 200 и `Cache-Control: no-store`, `Referrer-Policy: no-referrer`,
   CSP с script hash. Callback не должен попадать под SPA rewrite.
   В настройках OAuth зарегистрировать точный URI, показанный в диалоге.
2. В Firefox разрешить popup только этому origin, открыть DevTools Network/Console.
   Нажать «Подключить Яндекс», выбрать аккаунт и дать app_folder. Проверить S256,
   state и отсутствие client_secret в форме обмена. Не копировать секретные значения.
   После возврата адрес callback не содержит query/fragment, редактор в popup
   отсутствует. Если Яндекс показывает ошибку Client ID/Redirect URI без callback,
   исправить регистрацию; исходное окно не может прочитать чужую страницу ошибки.
3. Проверить OAuth POST /token отдельно: доступен ли ответ JavaScript, HTTP status,
   сообщения CORS и redirects. Затем нажать «Проверить доступ к API» и независимо
   записать результат `/info` и `app:/`. При необходимости дополнительных scope
   остановиться и записать ограничение, не расширять разрешения.
4. Только отдельным нажатием запустить тестовую передачу. Проверить запросы ссылки,
   PUT, ссылки скачивания и GET. Для каждого шага учитывать OPTIONS/preflight,
   Authorization/Content-Type, Access-Control-Allow-Origin; для preflight также
   Allow-Methods/Allow-Headers. Отсутствие OPTIONS на простом POST само по себе
   нормально. ACAO может быть скрыт для JS без Expose-Headers: смотреть Network,
   основной критерий — доступность ответа и совпадение прочитанных байтов.
   На подписанные URL OAuth-заголовок не отправляется. Не включать no-cors.
5. После сравнения нажать удаление **только** созданного тестового файла.
   При неудаче/неопределённом PUT сохранить показанный `app:/kartochnaya-probe-….txt`
   и удалить его вручную в исходном аккаунте. Не очищать папку приложения.
   Новая передача блокируется, пока остался отслеживаемый путь. После отключения
   удаление через прототип недоступно, чтобы не удалить путь в другом аккаунте.
6. Проверить отказ пользователя, закрытие popup, блокировку popup, отмену,
   неверный Redirect URI, отсутствие сети, reload. Открыть callback напрямую:
   при opener=null должно появиться объяснение, без обмена кода и без fallback.
   Повторить в Firefox Android: отдельная вкладка, возврат, фон, закрытие вкладки.
   Если COOP обрывает opener, ожидается безопасный отказ/таймаут, не расширение прав.
7. После ошибки убедиться в сохранении локального проекта и обычной работе Google
   Drive. В офлайне callback должен быть недоступен, а локальный редактор — доступен.
   Проверить хранилища: только публичный Client ID Яндекса сохраняется отдельно.
   Не публиковать HAR, полные URL запросов, скриншоты кодов/токенов или аккаунт-ID.
   В отчёт переносить только дату, браузер/версию, origin, шаг, HTTP status,
   безопасное описание preflight/CORS и итог сравнения/очистки.

## Выбор архитектуры 15В

Необходимость Netlify-посредника — **Не проверено**. Сейчас нет доказательства,
что он нужен, и нет доказательства, что прямой браузерный путь работает целиком.
Функция/proxy не добавлены. Следующий минимальный шаг — пройти сценарий выше
с реальным OAuth-приложением и аккаунтом на HTTPS Netlify origin. Если браузер
подтвердит блокировку `/token` по CORS, отдельно рассмотреть минимальный посредник
обмена в 15В, не делая выводов о Disk API и подписанных URL из результата OAuth.
Если блокируется только передача, сначала зафиксировать конкретный хост, preflight,
redirect и права, затем выбирать минимальную архитектуру.
