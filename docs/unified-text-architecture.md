# Единая горизонтальная раскладка текста — этап 1

## Решение
До стадии производственной эксплуатации пользователь разрешил отказаться от визуальной обратной совместимости прежнего Canvas-текста. Никакого преобразования документа при чтении или открытии нет: `element.text`, sparse UTF-16 `textRuns`, структура шаблонов, сохранение и история остаются прежними.

Ранее обыкновенный текст без `textRuns` проходил через `wrapLines()` и `drawTextGlyphs()` с Canvas `textBaseline='top'`. Первое изменение цвета создавало `textRuns` и переключало его на другой движок. Теперь обычные горизонтальные слои, **с `textRuns` или без них**, направляются в `richTextEngine.layout()` и `drawMixedTextGlyphs()`, единые для экранного Canvas и PNG.

Те же строки используются в `autoFitTextFont()`, `fitTextBoxToContent()` и подсветке фона `tf43Backdrop()`. `mobileV36BaseDrawText` не перекрывает новый режим старым. Отдельный предикат `supportsHorizontalTextLayout()` обозначает поддерживаемую геометрию независимо от наличия форматирования. `usesRichTextLayout()` пока оставлен для модели и экспериментального WYSIWYG: он означает *наличие диапазонов*, а не выбор рендерера.

## Известные границы этого PR
- Этот этап **не переписывает ввод**, DOM Selection, IME, мобильные панели и систему истории.
- `textarea` и флаг `experimentalTextWysiwyg` пока используют старые проверки допуска. В следующем PR потребуется убрать `plainWysiwygLayoutCompatible()` и проекцию старого baseline, заменив их проверкой соответствия DOM новому единому layout.
- Вертикальный текст, текст по пути, текст по контуру, текст по дуге, специальное выравнивание `justify` пока сохраняют свои отдельные режимы. Их перенос — отдельная задача, не стоит смешивать с горизонтальным WYSIWYG.
- Старые пиксельные эталоны и ожидания `top` baseline должны быть пересмотрены как **намеренно несовместимые** с новой отрисовкой. Нельзя просто удалить полезные проверки Canvas↔PNG, сохранения и редактирования.

## Технические критерии следующего этапа
1. Обычный слой с `Ваш заголовок` сразу использует WYSIWYG (без промежуточного textarea), поскольку больше не нужно сверять с устаревшей Canvas baseline.
2. Изменение цвета, размера и шрифта не переключает layout и не теряет Selection; no-op не мутирует модель.
3. При несовместимом DOM shaping пользователь получает понятный безопасный способ редактирования, но не через восстановление старого Canvas-движка.
4. `Ctrl+Z`, сохранение и экспорт остаются документированными тестами; полный CI обязателен до merge.

PR #102 — экспериментальный этап старой совместимости — **не следует объединять целиком** перед переходом к этому единому движку.
